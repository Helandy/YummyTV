# Плеер CVH: устройство, отказы узлов CDN и переезд на резервный

CVH (CdnVideoHub) — балансер, который отдаёт **прямые mp4-ссылки** на CDN `ok.ru` (`*.okcdn.ru`).
Никакой сессии, прокси и WebView, как у Alloha, здесь нет: два JSON-запроса к API и готовая лестница
качеств. Весь экстрактор — один файл на ~220 строк.

Но у этих ссылок есть две особенности, из-за которых простой балансер даёт самые загадочные обрывы:

1. **Подпись не зависит от узла.** Тот же файл с той же подписью доступен на резервном узле.
2. **Узел может «умереть» в любой момент**, при живом сроке действия подписи, и отдавать `400` на
   все новые соединения — при том что уже открытое соединение продолжает качать до конца.

Документ описывает механизм и то, как эти отказы обрабатываются. Пункты с ⚠️ — инварианты: места,
где «очевидная оптимизация» ломает воспроизведение. Раздел 4 — результаты замеров вживую, на них
опираются все решения ниже.

---

## 1. Общая схема

```
PlayerViewModel
  └─ PlayerStreamHandler.resolve()
       └─ ResolvePlayerStreamUseCase
            └─ DefaultPlayerStreamRepository.resolve()      ← кэш 3 мин по "iframeUrl|autoQualityLabel"
                 └─ CvhExtractor.extract()
                      ├─ GET plapi…/player/sv/playlist?pub=745&id=<animeId>&aggr=mali
                      │    └─ selectCvhItem() → vkId по серии + озвучке
                      ├─ GET plapi…/player/sv/video/<vkId>
                      │    ├─ sources.mpeg*Url  → лестница качеств
                      │    └─ failoverHost      ← резервный узел CDN
                      └─ Stream(url, headers = BROWSER_STREAM_HEADERS, qualities, failoverHost)

Media3 играет прямо по mp4-ссылке: OkHttpDataSource → CacheDataSource (50 МБ) → okcdn.ru
```

iframe-URL балансера выглядит так и парсится на параметры:

```
//ru.yummyani.me/iframeCVH.html?dubbing_code=AniLibria&anime_id=61316&episode=1&dubbing=…
```

⚠️ `anime_id` здесь — **внутренний id CdnVideoHub**, а не id аниме в yani. Совпадений ждать не надо.

## 3. Анатомия подписанной ссылки

```
https://vd752.okcdn.ru/?expires=1791393814371&srcIp=178.22.51.56&pr=90&srcAg=CHROME
  &ms=95.163.35.29&type=5&sig=9xvgvMx8TFw&ct=0&urls=178.237.29.10&clientType=46&id=13799800310512
```

| Параметр  | Смысл                                                               |
|-----------|---------------------------------------------------------------------|
| `id`      | Идентификатор видео, **одинаков у всех качеств**                    |
| `type`    | Вариант качества: `0`=240p, `1`=360p, `2`=480p, `3`=720p, `5`=1080p |
| `expires` | Срок действия в миллисекундах — **+24 часа** от выдачи              |
| `sig`     | Подпись                                                             |
| `srcAg`   | Класс клиента, под который подписана ссылка (`CHROME`)              |
| `srcIp`   | IP клиента на момент выдачи                                         |
| `ms`      | Адрес origin-сервера                                                |

⚠️ **`type` коллизирует между форматами.** У `hlsUrl` и у 480p один и тот же `type=2`, у `dashUrl` и
360p — `type=1`. Различает их только путь (`/video.m3u8` против `/`). Любая идентичность, собранная
из `id` + `type` без пути, склеит HLS с mp4. Сейчас плеер берёт только mp4 (у них `type` 0,1,2,3,5 —
все разные), но ключ кэша путь всё равно учитывает — на случай возврата HLS.

⚠️ **HLS и DASH из `sources` не используются намеренно.** В HLS-манифестах CdnVideoHub лежат
сегментные URL с сырыми IP-адресами CDN, и они **не** переписываются на `failoverHost` — это ломает
и загрузки, и переезд на резервный узел. Отсюда «нет Auto-качества» у CVH: только mp4.

## 4. Что измерено вживую (06.10.2026)

Замеры делались вне приложения, повторением ровно того же пути, что у плеера (`plapi` → playlist →
video → mp4 с Chrome-UA). Тайтл `anime_id=61316`, `vkId=13352552323824`, 1080p — 160 МБ / 1424 с.

**Чего НЕ происходит** (все три версии отвергнуты):

| Проверка                                                            | Результат                              |
|---------------------------------------------------------------------|----------------------------------------|
| Полный слив файла                                                   | 160 МБ за 15 с, без ошибок             |
| Три слива по одной подписи                                          | 480 МБ, без ошибок                     |
| Чтение пачками с простоем сокета 45 с (буфер профиля SMALL)         | **100 %**, 15 минут, ни одного обрыва  |
| Чтение пачками с простоем сокета 120 с (буфер профиля LARGE)        | **100 %**, 52 минуты, ни одного обрыва |
| 26 переоткрытий соединения за 25 минут (как плеер после паузы/seek) | все `206`                              |
| 40 запросов подряд по одной подписи                                 | все `206` — лимита по числу нет        |
| HTTP/2                                                              | ALPN отдаёт только `http/1.1`          |

То есть ни файл, ни узел, ни простой сокета, ни переоткрытие соединения обрывов не дают.

**Что происходит.** Ссылка в непредсказуемый момент перестаёт принимать **новые** соединения:

```
HTTP/1.1 400 Bad Request
Content-Length: 1
Connection: close
```

- Ловилось на ~6-й и на ~38-й минуте жизни ссылки; третья в 35 минут была ещё жива. Закономерности
  по возрасту нет, `expires` при этом стоит на +24 часа.
- Уже открытое соединение в этот момент **докачивает файл до конца** — обрыв видит только тот, кто
  открывает новое соединение.
- **Та же подпись на `failoverHost` отдаёт `206`.** Воспроизведено на обеих умерших ссылках. Значит
  умирает конкретный узел, а не подпись.

**Про User-Agent.** Подпись выдаётся под класс клиента (`srcAg=CHROME`), но проверка на запросе **не
сводится к «похоже на Chrome»**. Замер 07.10.2026: на каждый UA — свежая ссылка, по три запроса,
контрольный запрос эталонным UA до и после (строки с мёртвым контролем отбрасывались — узел в этот
момент мигал):

| User-Agent запроса                                 | Ответ     |
|----------------------------------------------------|-----------|
| Chrome 146–149 на **Windows**                      | `206`     |
| Chrome 146–149 на **Linux** (`X11`)                | `206`     |
| Chrome 125 на Android с `Mobile` (Pixel)           | `206`     |
| Chromecast / Google TV (`… CrKey/1.56`, синтетика) | `206`     |
| `ExoPlayerLib/…`                                   | `206`     |
| Chrome 146–149 на **macOS**                        | **`400`** |
| Chrome на Android **без** `Mobile`                 | `400`     |
| Safari, Firefox, `okhttp/4.12.0`, пустой, `abc`    | `400`     |

Выводы:

- ⚠️ **macOS-Chrome отклоняется.** Раньше UA выбирался `random()` из пула на 12 строк (по четыре на
  Windows, macOS и Linux) один раз на процесс, так что примерно **каждый третий запуск приложения не
  мог играть CVH до перезапуска**. Пул убран: теперь один константный UA (`BROWSER_USER_AGENT` в
  `core:utils`, Windows-Chrome), см. §8.
- Номер версии Chrome значения не имеет (146 и 149 взаимозаменяемы). Менять нельзя класс: ОС и
  мобильный вид.
- Запрос с отклоняемым UA подпись не «сжигает» надёжно: в одних прогонах контроль после плохих
  запросов проходил, в других нет (узел в это время мигал). Считать, что отклонённый UA мог
  испортить ссылку, и не полагаться на обратное.
- `User-Agent` обязан стоять на **каждом** пути, который трогает эти ссылки: воспроизведение и
  загрузки. Cast — исключение: там UA ставит сам Chromecast (§7).

`Referer`/`Origin` наоборот: с Chrome-UA и **без** `Referer` узел отдаёт `206`, а чужой
`Referer`/`Origin` вызывает `400`. Поэтому `CvhDownloadStrategy` ставит `skipRefererOrigin = true`.

## 5. Переезд на резервный узел

Цепочка от отказа узла до продолжения воспроизведения:

```
okcdn отдал 400
  └─ PlayerLoadErrorHandlingPolicy.getRetryDelayMsFor() → C.TIME_UNSET     ← быстрый фатал, 1 запрос
       └─ PlayerListenerEffect → PlaybackException.toPlaybackErrorEvent()
            └─ httpStatusCode() = 400                                      ← типизированный код
                 └─ DefaultSourceBehavior.onPlaybackError()
                      ├─ 400 ∈ FAILOVER_HTTP_CODES
                      ├─ state.availableFailoverHost() = "vd591.okcdn.ru"
                      └─ applyHostFailover()
                           ├─ host.update { withFailoverHost(host) }       ← подмена в состоянии
                           └─ host.invalidateStreamCache()                 ← кэш резолва
                                └─ PlayerMediaItemUpdater: url изменился → setMediaItem + prepare
```

Что здесь важно:

- **Никаких запросов к `plapi`.** Подменяется хост в ссылках, которые уже лежат в состоянии. Раньше
  на `400` шёл полный перерезолв (playlist + video) ради смены имени хоста в готовом URL — это и
  было той видимой заминкой. Срабатывало ровно тогда, когда плеер открывает новое соединение: после
  паузы, перемотки, смены качества.
- ⚠️ **Подменяется вся карта качеств**, а не только `streamUrl`. Иначе переключение качества после
  переезда вернёт зрителя на отказавший узел: фактический URL плеера берётся из `streamQualityMap`
  по метке качества (`PlayerPlaybackUiStateMapper`), а не из `streamUrl`.
- ⚠️ **Бюджет тихих повторов (`MAX_ATTEMPTS = 5`) не тратится.** Переезд — не повтор того же
  ресурса, а переход на доказанно живой узел ценой одного `setMediaItem`, а не двух сетевых
  запросов. Поэтому ветка стоит **выше** проверки `retry.canRetry()`.
- ⚠️ **`retryKey` не бампается, и это не упущение.** `PlayerMediaItemUpdater` пересоздаёт media item
  при `currentUri != config.url`, а переезд по определению меняет URL. `retryKey` нужен для
  обратного случая — когда ссылка не изменилась.
- **Защита от зацикливания — без отдельного флага.** После подмены хост ссылки равен
  `streamFailoverHost`, и `availableFailoverHost()` возвращает `null`. Флаг пришлось бы сбрасывать в
  трёх точках (`reset()`, `onPlaybackReady()`, `onStreamResolved()`) — лишний источник рассинхрона.
- **`recovering` не выставляется**, зато выставляется `isPlaybackRecovering`: последний кадр
  остаётся на экране (`keepContentOnReset`), оверлея нет, а флаг снимется сам по `PlaybackReady`.
- **Если и резервный узел отдал `400`** — `availableFailoverHost()` даст `null`, и управление упадёт
  в обычный `scheduleRetryAttempt()` с `forceRefresh = true`, то есть в полный перерезолв, где
  `CvhExtractor` сам переведёт все качества на `failoverHost`. Отдельного кода для этого нет.

`FAILOVER_HTTP_CODES = {400, 403}`. `404`/`410` сюда **не** входят: это «файла нет», и там нужен
настоящий перерезолв, а не другой узел.

⚠️ **`FATAL_RESPONSE_CODES` в `PlayerLoadErrorHandlingPolicy` — это контракт.** Быстрый фатал на
`400` — единственное, что доносит отказ узла до слушателя плеера за один запрос вместо того, чтобы
утопить его в 20 фоновых ретраях загрузчика (`SILENT_RETRY_COUNT`). Менять набор, не посмотрев на
`DefaultSourceBehavior.FAILOVER_HTTP_CODES`, нельзя — переезд просто перестанет срабатывать.

Отдельно от этого в `CvhExtractor` есть исходный механизм: сырые IPv4-хосты в `sources`
переписываются на `failoverHost` **всегда**, а именованный узел — только при `forceRefresh`
(перерезолв после сбоя). Поле `failoverHost` в `Stream` отдаётся пустым, если ссылки уже выданы на
этом узле — переезжать тогда некуда.

## 6. Кэши: их два, и они про разное

**Кэш резолва** — `DefaultPlayerStreamRepository`, in-memory, TTL 3 минуты, 8 записей, ключ
`"iframeUrl|autoQualityLabel"`. Нужен, чтобы не ходить в `plapi` при смене качества и повторном
входе в плеер. После переезда на резервный узел сбрасывается через
`InvalidatePlayerStreamCacheUseCase` — иначе в пределах TTL он поднял бы ссылки на отказавший узел.

**Онлайн-кэш воспроизведения** — `SimpleCache` на 50 МБ, `PlayerStreamingCacheProvider`. Ключ по
умолчанию — полный URI, а он у подписанных ссылок меняется при каждом перерезолве и при переезде.
Поэтому для okcdn ключ нормализуется до идентичности файла (`id` + `type` + путь):

```
okcdn|13799800310512|5|
```

Без этого уже скачанный буфер после смены ссылки недостижим, 50 МБ забиваются копиями одного файла,
а переезд на резервный узел начинает загрузку с нуля.

⚠️ Нормализация узкая, только для okcdn-хоста; всё остальное уходит в `CacheKeyFactory.DEFAULT`.
Срезать подпись у произвольного CDN нельзя — можно склеить разные дорожки одного манифеста. ⚠️
Фабрики ключей офлайн-загрузок (`DownloadCacheKeyFactory`, `RotatingHlsCacheKeyFactory`) трогать
нельзя вообще: от них зависит идентичность уже скачанных на устройство байтов.

## 7. Cast: работает со штатным ресивером

Приложение работает со штатным Cast-ресивером (`DEFAULT_MEDIA_RECEIVER_APPLICATION_ID`). Он за медиа
ходит **собственным браузерным стеком Chromecast** и своих заголовков к запросам не добавляет, а
значит, `User-Agent` там не наш. Для CVH это не помеха: okcdn проверяет класс UA, и UA самого
Chromecast принимается (§4, замер 07.10.2026).

⚠️ **Чего не проверено.** Замер сделан `curl` по синтетическим строкам с `CrKey/1.56`, а не по UA,
захваченному у реального устройства; на самом Chromecast Cast для CVH после этих правок не
запускался. Узнать настоящую строку просто: поднять на компьютере в той же сети HTTP-сервер,
печатающий заголовок `User-Agent`, скастить на него тестовую mp4-ссылку и сверить строку с таблицей
в §4. Если на устройстве всё же `400`, вопрос решается прокси в LAN, а не своим ресивером.

⚠️ **Урок.** Раньше кнопка Cast скрывалась для okcdn-потоков (`canCast`) из предположения «ресивер
не может поставить Chrome-UA». Замером это не проверялось, и запрет отключал рабочую функцию:
коммит `d13d0e6bf` («Cast video») как раз чинил Cast для okcdn-ссылок, у которых нет расширения в
пути и из-за этого не определялся контейнер (лечится `video/mp4` в `YummyTvCastMediaItemConverter`).
Запрет снят. Не скрывать функцию по логическому выводу — только по замеру на устройстве.

### Почему не свой ресивер

Собственное Web Receiver приложение (CAF) для CVH ничего не даёт и стоит дорого: регистрация в Cast
Developer Console (разовый взнос), HTTPS-хостинг страницы и публикация (до неё работает только на
зарегистрированных устройствах). Заголовки в нём навешиваются лишь на XHR-запросы адаптивных потоков
(`segmentRequestHandler` и подобные), а `User-Agent`, `Referer`, `Origin`, `Sec-*` из браузерного JS
не ставятся, и запросы `<video>` для прогрессивного mp4 не настраиваются вовсе.

Не помогает он и Alloha: ей нужны именно запрещённые для JS заголовки сессии, а её прокси слушает
`127.0.0.1`, который Chromecast не видит. Кастить Alloha можно только прокси, слушающим в LAN
(токены, белый список клиента по IP устройства, иначе это открытый прокси) — это отдельная большая
задача, она не делалась.

Проброс заголовков в `MediaInfo.customData` тоже отвергнут: в `play-services-cast 22.3.1` нет
copy-конструктора `MediaInfo.Builder(MediaInfo)`, а штатный ресивер эти данные всё равно игнорирует.

## 8. User-Agent: настройка из проверенного списка

UA для запросов к балансерам и их CDN выбирает пользователь: **Настройки → Плеер → «User-Agent
балансеров»** (TV и mobile). Выбор — из закрытого списка `BrowserUserAgentProfile`
(`core/model/.../settings/`): Windows·Chrome (по умолчанию), Linux·Chrome, Android·Chrome.
Свободного текста нет намеренно: okcdn принимает не любой браузерный UA (таблица в §4), и
произвольная строка тихо ломает CVH — `400` на всё без объяснения причин.

Как это устроено:

- `BrowserUserAgentProvider` (`core/utils/.../network/BrowserUserAgent.kt`) — контракт; реализация
  `DataStoreBrowserUserAgentProvider` в `core:preferences` держит профиль в `StateFlow` и отдаёт
  строку синхронно. Потребители читают её **в момент запроса**, а не кэшируют: экстракторы (CVH,
  Kodik, VK, Rutube, Sibnet, Aksor, Zedfilm), превью Kodik.
- Применяется к **следующему резолву**: уже играющий поток держит заголовки, с которыми его
  получили, а резолв кэшируется на 3 минуты (`DefaultPlayerStreamRepository`). Для смены UA на лету
  серию достаточно перезапустить.
- До первого чтения DataStore провайдер отдаёт профиль по умолчанию. Это безопасно: все профили из
  списка принимаются CDN, расходиться могут только заголовки самого первого запроса холодного
  старта.
- Загрузки берут UA из заголовков, которые вернул экстрактор, то есть тоже из выбора пользователя.
  `BROWSER_USER_AGENT` (профиль по умолчанию) подставляется только когда экстрактор UA не передал.
- **Alloha в настройку не входит**: её UA случаен per-process намеренно (отпечаток обязан быть
  стабилен между сессиями) и относится к другому CDN.

⚠️ **Чтобы добавить профиль**, строку нужно сначала проверить на живой ссылке: свежая ссылка + три
запроса + контроль независимым UA до и после (§9). Профиль, который okcdn отвечает `400`, в списке
оказаться не должен — иначе пользователь сам себе сломает CVH. Номер версии Chrome значения не
имеет, а вот ОС и мобильный вид — да (macOS отклоняется).

Бывшая гипотеза этого раздела — «подпись, выданная одному процессу, после его смерти переигрывается
с другим случайным UA и мгновенно даёт `400`» — **не подтвердилась**: Windows- и Linux-Chrome разных
версий взаимозаменяемы. Реальный дефект был другим: раньше UA брался `random()`
из пула на 12 строк, четыре из которых были macOS, и сервер их отклоняет.

## 9. Отладка

Логи идут через `AnalyticsTracker.log` — в дебаге в logcat, в релизе no-op.

```bash
adb logcat -c && adb logcat -v time PlayerViewModel:D CvhExtractor:D Analytics:D *:S
```

| Маркер                                         | Значение                                                                                                                              |
|------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------|
| `Resolved vkId=… qualities=[…] failoverHost=…` | Резолв прошёл. Пустой `failoverHost` — переезжать будет некуда.                                                                       |
| `useFailoverHost=true`                         | Это перерезолв после сбоя: все качества переведены на резервный узел.                                                                 |
| `Playback error … http=400`                    | Узел отказал. Если дальше нет `CDN host failover` — не было резервного.                                                               |
| `CDN host failover -> vdNNN.okcdn.ru`          | Переезд выполнен, запросов к `plapi` не было.                                                                                         |
| `Silent playback retry attempt=N/5`            | Переезд недоступен или уже израсходован — идёт обычный перерезолв.                                                                    |
| `Silent playback retry with /videos refresh`   | Повреждённый контейнер: перезапрос `/videos` за свежим iframe.                                                                        |
| `host_failovers` в отчёте об ошибке            | Сколько раз за сеанс переезжали. Ошибок в аналитике станет меньше — часть `400` гасится до фатала, и без этого поля эффект незаметен. |

### Воспроизвести вручную

```bash
UA="Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/149.0.0.0 Safari/537.36"
# 1. плейлист: найти vkId нужной серии и озвучки
curl -s "https://plapi.cdnvideohub.com/api/v1/player/sv/playlist?pub=745&id=61316&aggr=mali" \
  -H "Referer: https://ru.yummyani.me/" -A "$UA" | python3 -m json.tool | head -40
# 2. ссылки и резервный узел
curl -s "https://plapi.cdnvideohub.com/api/v1/player/sv/video/13352552323824" \
  -H "Referer: https://ru.yummyani.me/" -A "$UA" | python3 -m json.tool
# 3. живость узла (206 — жив, 400 — отказал)
curl -s -o /dev/null -A "$UA" -H "Range: bytes=0-65535" "<mpegFullHdUrl>" -w "%{http_code}\n"
# 4. та же подпись на резервном узле
curl -s -o /dev/null -A "$UA" -H "Range: bytes=0-65535" \
  "$(echo '<mpegFullHdUrl>' | sed 's|vd752\.okcdn\.ru|vd591.okcdn.ru|')" -w "%{http_code}\n"
```

⚠️ **Про измерения.** Момент смерти узла непредсказуем (ловился и на 6-й минуте, и на 38-й, и не
наступал к 35-й), поэтому по одному прогону выводов делать нельзя. Если нужен сам отказ, а не
ожидание — проще дождаться его на устройстве, поставив серию на паузу на несколько минут и сняв с
паузы: плеер переоткроет соединение.

## 10. Нумерация серий и выбор элемента плейлиста

`selectCvhItem` (`CvhPlaylistItem.kt`, покрыт `CvhPlaylistSelectionTest`) разбирается с тем, что
плейлист CVH плоский: все озвучки всех серий одним списком.

- `isSerial = false` (фильм) — фильтр по номеру серии не применяется; поле `episode` может быть
  `null`.
- Озвучка ищется в три ступени, потому что `dubbing_code` не всегда равен `voiceStudio`:
  локализованное название студии приезжает транслитом (`ort` против `ОРТ`), и так, как в плейлисте,
  его пишет только метка `dubbing` («Озвучка Дубляж ОРТ», префикс `Озвучка ` отрезается):
  `voiceStudio == dubbing_code` → `"voiceType voiceStudio" == label` → `voiceStudio == label`.
- Если не подошло ничего, берётся первый подходящий по серии кандидат: лучше чужая озвучка, чем
  пустой экран.
- `voiceStudio` у субтитровых дорожек приходит как JSON `null`, а `optString` превратил бы это в
  строку `"null"` — отсюда `optStringOrEmpty`.

Оба запроса идут через `fetchJsonWithRetry`: один повтор через 700 мс. HTTP-ошибка бросает
исключение, а не маскируется под `JSONException` на HTML-теле — иначе сбой сети на слабой приставке
выглядел бы как «плейлист без items».
