# Восстановление входа через Block Store

После переустановки приложения или переезда на новое устройство (перенос данных с телефона,
восстановление из облачной копии Google) пользователь остаётся залогиненным в Yani. Работает на
телефоне и на ТВ, если на устройстве есть Google Play Services.

## Зачем отдельное хранилище

Refresh-токен лежит в `SecureYaniAuthPreferences`, зашифрованный ключом Keystore конкретного
устройства, поэтому он исключён из Auto Backup (`app/src/main/res/xml/backup_rules.xml`,
`data_extraction_rules.xml`): на другом устройстве его не расшифровать.

[Google Block Store](https://developer.android.com/identity/block-store) хранит небольшие данные
приложения внутри Google Play Services, отдельно от его данных. Они переживают переустановку и
очистку данных и попадают на новое устройство при переносе или восстановлении из облака.
Backup-правила не меняются. Block Store не синхронизация: на уже установленных устройствах запись
видна только локально.

## Защита токена

Токен кладётся в Block Store как есть, без нашего шифрования: ключ Keystore привязан к устройству, и
зашифрованный им токен на новом устройстве нечем расшифровать. Защищает Google Play Services:

| Где лежит токен                            | Чем защищён                                                                                |
|--------------------------------------------|--------------------------------------------------------------------------------------------|
| Локально, в хранилище Google Play Services | Песочница Android и шифрование диска; запись читает только приложение с той же подписью    |
| Облачная копия в аккаунте Google           | E2E-шифрование ключом из PIN, графического ключа или пароля блокировки; у Google ключа нет |
| Прямой перенос устройство → устройство     | Зашифрованный канал между устройствами                                                     |

Без блокировки экрана E2E-шифрование недоступно, и Block Store не отправляет данные в облако даже
при
`setShouldBackupToCloud(true)`: токен переедет только при прямом переносе. Локальная копия защищена
примерно как наш режим `TokenStorageMode.FALLBACK`, песочницей без Keystore. Для refresh-токена,
который отзывается выходом из аккаунта, это приемлемо.

Если понадобится строже: писать только при `isEndToEndEncryptionAvailable() == true` (без блокировки
экрана восстановления не будет совсем) или выставить `setShouldBackupToCloud(false)` (только прямой
перенос и переустановка на том же устройстве).

## Как устроено

Одна запись с ключом `yani_refresh_token`, `setShouldBackupToCloud(true)`. Токен пишется при каждом
изменении: сервер может ротировать его на refresh.

| Когда                                            | Что делаем                 | Где                                              |
|--------------------------------------------------|----------------------------|--------------------------------------------------|
| Вход (пароль, QR/NSD, подтверждение регистрации) | `save(token)` после успеха | `YaniAccountRepository.signInWithTokenInternal`  |
| Обновление токена                                | `save(token)`              | `YaniAccountRepository.refreshToken`             |
| Смена пароля                                     | `save(token)`              | `YaniProfileSettingsRepository.changePassword`   |
| Явный выход                                      | `clear()`                  | `YaniAccountRepository.logout`                   |
| Старт главного экрана без сессии                 | `restore()` → вход         | `MainViewModel` → `RestoreAccountSessionUseCase` |

Файлы:

- `feature/account/data/.../data/account/backup/AuthTokenBackup.kt` — контракт data-слоя;
- `feature/account/data/.../data/account/backup/BlockStoreAuthTokenBackup.kt` — реализация;
- `feature/account/domain/.../usecase/RestoreAccountSessionUseCase.kt`;
- `feature/main/presentation/.../handler/MainSideEffectsHandler.kt` — `restoreAccountIfMissing()`.

## Восстановление

`AccountRepository.restoreSessionFromBackup()`:

1. Если сессия уже есть, ничего не делает.
2. Достаёт токен из Block Store; нет записи — выходит.
3. Прогоняет токен через тот же атомарный `signInWithTokenInternal`, что и обычный вход: `GET
   /profile` с этим токеном, потом запись токена, профиля и настроек, при ошибке откат.
4. Успех — событие `account_session_restored_from_backup`. UI отдельно не уведомляется:
   `observeAccountSession()` сам переключит экраны.

Вызывается перед `refreshAccountIfStale()`, поэтому восстановленный токен сразу попадает под обычное
обновление.

## Когда запись удаляется

- Явный выход из аккаунта: иначе вход «воскрес» бы при следующем запуске.
- Сервер отверг токен (`401`/`403` на `GET /profile`): чтобы не долбиться с ним на каждом старте.

Сетевые ошибки запись не трогают. Не удаляется она и при откате неудачного входа, и когда чтение из
Keystore вернуло пусто: на кастомных прошивках Keystore ненадёжен (`TokenStorageMode.FALLBACK`), и
бэкап как раз страхует этот случай.

## Без Google Play Services

Все вызовы Block Store best-effort: на приставках без GMS `Task` падает, ошибка пишется в
`AnalyticsTracker.log` (тег `AuthTokenBackup`) и глотается. Вход, выход и обновление токена работают
как раньше, без бэкапа.

## Ограничения

- Восстановленное устройство использует ту же серверную сессию (тот же refresh-токен). Если yani при
  refresh инвалидирует прежний токен, одно из устройств разлогинится. Для переезда это приемлемо.
- Без блокировки экрана облачной копии нет.

## Как проверить

Нужен эмулятор или устройство с Google Play Services.

1. Войти в аккаунт: в logcat нет ошибок с тегом `AuthTokenBackup`.
2. `adb shell pm clear su.afk.yummy.tv.debug`, запустить: вход восстановлен без экрана логина.
3. Выйти из аккаунта, `pm clear`, запустить: входа нет (запись удалена).
4. Устройство без GMS: вход и выход работают, в logcat только пойманные ошибки `AuthTokenBackup`.
